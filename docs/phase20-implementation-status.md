# Phase 20 의료기관 연동 구현 현황

본 기능은 연구·교육 및 시스템 통합 검증용이다. 질병 진단, 촬영 재지시, 임상적으로 검증된 보고서를 제공하지 않는다.

## 구현 및 자동 검증 범위

- REQ-20-01: DICOM UID 해시 기반 검사/시리즈/인스턴스 그룹화와 중복 SOP 차단
- REQ-20-02: DB 관리형 촬영 프로토콜 및 완전성 판정
- REQ-20-03: 생성 근거를 포함한 검색 태그와 권한 기반 수정
- REQ-20-04: 관리자 입력형 SNOMED CT/RadLex/DICOM 매핑 구조. 임의 코드는 제공하지 않음
- REQ-20-05: `UNVERIFIED`, `PARTIAL`로 표시되는 실험용 DICOM SR 생성
- REQ-20-06: 외부 전송 없는 FHIR R4 예제 Bundle 생성
- REQ-20-07: HMAC 서명과 로컬 전송 대기열. 실제 HTTP 전송은 비활성화
- REQ-20-08: 우선순위·활성화·버전이 저장되는 규칙 기반 라우팅
- REQ-20-09: 경로 조작, 심볼릭 링크, 중첩 ZIP, 크기·개수·압축률 검사
- REQ-20-16: predictive entropy와 probability margin 계산
- REQ-20-22: 권한 보호된 관리자 상태 API와 UI

## 미구현 및 이유

- REQ-20-10~15, 17~19: 실제 공개 데이터 라이선스 동의·다운로드 및 검증 데이터/승인 모델 아티팩트가 필요하다. 데이터나 실모델 없이 완료로 표시하면 허위가 되므로 구현하지 않았다.
- REQ-20-07 실제 웹훅 전송/재시도 worker: 외부 수신 URL과 Redis/Celery 실행 환경이 없어 로컬 대기열까지만 구현했다.
- REQ-20-20 백업·복구 실행: 운영 PostgreSQL, MinIO, 모델 저장소와 조직 보존정책이 필요하다.
- REQ-20-21 전체 장애 시뮬레이션: Redis, Celery, Orthanc, MinIO가 현재 프로젝트 실행 구성에 포함되지 않아 해당 장애를 성공적으로 복구했다고 검증할 수 없다.
- REQ-20-23 모든 합성 해부학 형태: 기존 합성 DICOM 변형은 시스템 흐름 검증용이며 해부학적 사실성을 보장하지 않는다.
- REQ-20-24 전체 학습→MLflow→승인→ONNX→배포 E2E: 데이터셋과 승인된 모델이 없어서 기존 업로드→검토→감사→재학습 후보→보고서 흐름만 검증한다.

실제 연동을 활성화하려면 조직별 개인정보 처리, 네트워크, 비밀키, 용어 라이선스, 보존정책 및 임상 검증 승인이 선행되어야 한다.
